# 차시 작성 지침 (8차 F·G — 검토 문서 → 코드)

이 문서는 차시를 쓰는 사람(사람이든 에이전트든)이 지켜야 하는 것을 한 장에 모은 것이다. 근거는 `docs/8차_변경지시서_전면개편.md` 4·6·8·9·10절과 `CLAUDE.md`. 본보기는 `docs/검토/method-01.md` 와 `src/content/courses/method/lesson01.ts` — **둘을 먼저 읽는다.**

## 만드는 것 (차시마다)

1. `docs/검토/<과목>-<nn>.md` — 10.1 의 꼴 그대로. `audit:draft` 가 줄머리(`중심 질문`, `학습목표    1`, `질문`, `선택지`, `### 카드 N ─ 이름`, `기준      1`, `과제`, `검사   정답:` `갈림:` `이해:` `상황:`, `문항`)를 읽어 코드와 **글자 그대로** 대조한다. 문서에 쓴 문장을 코드에 그대로 옮긴다.
2. `src/content/courses/<과목>/lesson<nn>.ts` — `export const lesson: Lesson = { … }`. 네 검사는 `checks` 필드와 **코드 주석 양쪽**에 (주석에 `정답:` `갈림:` `이해:` `상황:` 네 줄).
3. `src/content/courses/<과목>/index.ts` — 색인 한 줄 + `loaders` 한 줄. **다른 사람의 줄은 건드리지 않는다** (여러 사람이 같은 파일에 자기 줄만 더한다). `idx(id, order, title, centralQuestion, published, legacyStepIds?)` — 교육론은 `idx(id, order, layout, title, centralQuestion, published, legacyStepIds?)`.
   - published: 교수법 01~07 `true`, 08~18 `false`. 교육론 01~02 `true`, 03~12 `false`.
   - legacyStepIds: 교수법은 옛 파일(`git show e4d35c4:src/content/lessons/lessons02to07.ts` · `lessons08to13.ts` · `lessons14to18.ts`)의 그 차시 `steps[].id` 목록. 교육론 02~12 는 `EDU_LEGACY_STEP_IDS`.
4. 공개 차시(교수법 02~07 · 교육론 02)는 **이론 배경**이 있어야 한다 (`verify:theory`): 카드마다 `linkedConceptId` 로 붙은 항목이 하나 이상, `plainTerms` 의 문구가 본문(what·why·inClass·keyPoints·confusedWith·more·objectives·과제 등)에 글자 그대로 있어야 한다.
   - 교수법 02~06 은 `src/content/theory/t02.ts`~`t06.ts` 가 이미 있다. 개념이 같으면 옛 카드 id(`c02-…`)를 그대로 써서 링크를 살리고, `plainTerms` 는 새 본문에 있는 문구로 고친다. 새 카드에는 항목을 하나 더하거나 `linkedConceptId` 를 옮긴다.
   - 교수법 07 은 `t07.ts` 를 새로 쓴다 (항목 2~4개, `verified: false`, `TheoryEntry` 의 필수 필드 전부: id · termKo · termEn · scholars[{nameKo,nameEn,year?}] · claim · bridgeToPlain · limits · textbookRef · readings[] · oneLine · verified · linkedConceptId · plainTerms). `theory/index.ts` 의 `method` 에 등록.
   - 교육론 02 는 `te02.ts` 를 새로 쓰고(80분 차시는 카드가 6장 이상이라 항목도 카드마다 하나씩, 6개 이상) `theory/index.ts` 의 `edu` 에 등록. 교육론 03~12 · 교수법 08~18 은 이론 배경 없이 둔다 (미공개).
   - 인명·연도는 확실한 것만. 모르면 `verified: false` 로 두고 원문 인용은 넣지 않는다. 교재 심화 읽기에서 복사하지 않는다.

## 차시의 모양 (4절 · 검증기가 센다)

- `layout`: 교수법 `'method'`(도입 · 개념 · **활동 1 · 활동 2** · 정리 — 강의자 지시 2026-09-22) · 교육론 2~5강 `'edu80'`(개념·활동이 두 벌 — `concepts2`, `activity2`) · 6~12강 `'edu40'`. 단계마다 시간을 적지 않는다 — 검토 문서의 절 제목에도 (강의자 지시 2026-09-18).
  - 교수법 **활동 1**(`activity1`, 단계 id `activity-1`)은 개념 문항보다 현실적이고 생각할 거리가 있되 **비교적 답이 있는** 문제다. 질문 · 고르거나 쓰기 · 서로의 답 보기(광장)까지만 — `group` · `game` 이 없다. `checks.answer` 에는 「정답은 없다」가 아니라 **그 답과 근거**를 적는다. 검토 문서에는 `## 활동 1` 절로 쓴다 (`상황 · 과제 · 칸 · 공유 · 모둠 없음 · 게임 없음 · 검사`).
  - 교수법 **활동 2**(`activity`, 단계 id 는 그대로 `activity` — 이미 낸 응답이 그 아래에 있다)는 정답이 없는 **중립적 토의 문제**다. 정답 검사에서 한 문장의 답이 말해지면 상황을 바꾼다. 검토 문서에는 `## 활동 2`.
- 차시 머리: `title` · `centralQuestion`(물음표로 끝남) · `objectives` 셋(「~를 구분한다」 「~를 고른다」 꼴, 「이해한다」 「안다」 금지).
- `intro`: `stimulus` 하나(200자 안팎, `label: '수업용으로 만든 가상 자료'`) + `prompt` + `kind: 'choice'`(options 3~5개) 또는 `'line'`.
- `concepts`: 교수법 3~4장 · edu80 각 부 3~4장 · edu40 2~3장. 카드 id 는 앱 전체에서 고유 (`c<nn>-<slug>`, 교육론은 `e<nn>-<slug>`).
  - `what` 3~4문장 · `why` 2~3문장 · `inClass` 3~4문장 — 문단 하나씩(줄바꿈 없음). 정의 → 예 순서.
  - `keyPoints` 정확히 3줄. 한 줄은 「~다」로 끝나는 완전한 문장이고 다음 중 하나의 꼴: 「~이(가) 아니라 ~다」 / 「~(으)면 ~다」 / 「~를 보면 ~를 알 수 있다」. 명사 나열 금지. 세 줄이 서로 다른 말.
  - `confusedWith`(선택) 한두 문장. `more`(선택) {title, body} — body 는 문단마다 4문장 이하.
  - `check` **잠깐 확인** — 카드마다 4지선다 하나, 이유 칸 없음 (강의자 지시 2026-09-18). 검토 문서의 카드 끝에 먼저 쓰고 `npm run sync:checks -- <과목>-<nn>` 으로 코드에 옮긴다:
    ```
    확인      장면 한 문장. 가장 ~한 것은?
              ① 보기
              ② 보기
              ③ 보기
              ④ 보기
              정답 ②
    ```
    카드의 기준을 새 장면에 써야 풀리게 묻는다 — 「교실에서」 장면을 되풀이하지 않고, 정의를 되묻거나 부정으로 묻지 않는다. **교수법은 답이 하나뿐인 물음이어야 한다** (강의자 지시 2026-09-22): 「가장 알맞은 것은?」이 아니라 「~인 것은?」 「~에 해당하는 것은?」으로 묻고, 오답 셋은 카드의 기준 한 줄과 정면으로 어긋나게 둔다 — `verify:concepts` 가 교수법 물음의 「가장」·「알맞은」을 막는다. 오답마다 흔한 오해 하나를 담는다. 보기 넷은 같은 꼴이고 길이가 비슷하다 — 정답이 가장 긴 보기가 되는 버릇을 만들지 않는다. 카드 문장을 16자 넘게 옮기지 않고, 카드 이름을 정답에만 넣지 않는다. 정답 자리는 과목 전체에서 고르게.
- `activity` (edu80 은 `activity2` 도):
  - `situation`: `format: 'dialogue' | 'studentWork' | 'card' | 'article'`, `label: '수업용으로 만든 가상 자료'`, `body` **200~400자**(공백 포함). dialogue·studentWork 는 모든 줄이 「꼬리표␣␣내용」(공백 두 칸) 꼴 — 지문 줄도 `장면   …` 처럼 꼬리표를 붙인다. 괄호만 있는 줄 `(1분)` 은 지문으로 허용.
  - `task`: 명령형 **한 문장**, 「~하세요/쓰세요/고르세요/정하세요/나누세요/적으세요/놓으세요/매기세요/배분하세요」로 끝남. 물음표 금지. 「이 상황에서 교사로서 ___를 정하고 이유를 쓰세요」 꼴.
  - `fields`: 1~2개, 전부 `required: true`. **칸마다 `help` 한 줄** — 무엇을 보고 무엇을 쓰는지(예: 「보고서의 어느 줄이 근거인지 적는다」). 화면의 과제 블록이 이 줄을 「무엇을 쓰나」로 그대로 보인다 (`audit:activity`). 선택형(`choice`)은 options 3개 이상. `allocation`·`rank`·`sort` 는 items 4개 이상, `sort` 는 `bins` 2개.
  - `share.prompt` 한 줄. `group` {format, fieldKey, prompt, repPrompt?(sentence·vote 필수), reasonKey?(vote 필수)} — 형식과 칸 종류: allocation↔allocation · rank↔rank · vote↔choice · sentence↔longtext/text · sort↔sort.
  - `game`: 아래 배치표. `gameOptions` 는 rps `{pick:'winner'|'firstOut'}` · flash `{pick:'fastest'|'slowest'}` · marble `{map, pick}`(맵 id 와 발표자 규칙 — `src/lib/marble.ts`) 만.
  - `checks` {answer, split, understand, situation} — 정답 검사(정답을 한 문장으로 말할 수 없어야 한다) · 갈림(선택지마다 고를 만한 이유 한 문장씩) · 이해(30초 안에 무엇을 쓸지 아는가) · 상황(과학교사가 실제로 맞닥뜨리는 장면인가).
- `wrapup.prompt`: 「오늘 활동에서 내 결정의 근거가 된 개념은 무엇이었고, 그 개념이 없었다면 무엇을 달리 했겠는가」 꼴 — 「근거가 된 개념」과 「없었다면」 두 말이 반드시 들어간다. 활동에 맞게 「무엇을 달리 했겠는가」만 바꾼다.

## 글쓰기 (9절 · `verify:wording`)

- 학생이 읽는 문장의 어미는 「~다」 「~하세요」 둘뿐. 「~해 봅시다」 「~해요」 「~예요」 「~네요」 금지 (자료 본문 속 학생·교사의 말은 예외 — 대본은 그 사람의 말이다).
- 한 문장 60자 이하. 한 문단 4문장 이하. 느낌표 금지(대본 속 발화는 예외). 「자, 」로 시작 금지.
- 비유 금지: 빈 그릇·렌즈·나침반·뼈대·씨앗·근육·항해·작은 과학자·다리를 놓·문을 연다·지도처럼·「마치 ~처럼」. 구호(「기억하세요」 「핵심은 하나」) · 다짐(「하겠습니다」 「약속」) · 부추김(「멋진」 「놀라운」 「흥미로운」) · 이모지·별표 · 교재 냄새(「~에 대해 알아보자」 「~를 살펴보면」 「~라 할 수 있다」 「~의 중요성」) 금지.
- 학생이 읽는 글에 「○분」을 쓰지 않는다. 교실 장면 속 시간(「20분 동안」)이 꼭 필요하면 그 줄 바로 위에 `// wording-ok: 교실 장면 속 시간` 주석.
- 앞 차시 번호(「12강에서」)로 뒤 차시를 부르지 않는다 — 「나중에」.
- 두 과목은 자료·상황·과제·개념 문장을 공유하지 않는다 (`verify:course` 가 12자 이상 같은 문장을 잡는다). 다른 차시와도 같은 문장을 쓰지 않는다 (`verify:content`).
- **물리 소재는 줄인다** (강의자 지시 2026-09-22 — 학생들이 어려워한다). 새 장면은 생물·화학·지구과학에서 먼저 찾고, 한 차시에 물리 장면은 하나쯤으로 둔다. 없애는 것이 아니라 줄이는 것이다.
- 교재 OCR 오독(「히는」 「시용」 「결괴」 「비고츠기」 …)과 반복 템플릿(「~이(가) 학생의 설명과 교사의 선택을 어떻게 바꾸는가」 「정의를 외우기보다」)이 들어오면 실패한다.

## 장면과 대사 — 이론을 보이려고 지어낸 상황극을 쓰지 않는다 (강의자 지적 2026-09-22)

도입 자료 · 활동 상황 · 카드의 「교실에서」 · 잠깐 확인의 장면 전부. 검증기가 못 세는 것이라 **쓰는 사람이 넷을 스스로 묻는다.** 하나라도 「아니다」면 다시 쓴다.

1. **그 학생이 정말 그렇게 말하는가.** 중학생의 입말로, 짧게. 「무엇을 배웠는지는 잘 모르겠어요」처럼 교사가 듣고 싶은 고백을 학생 입에 넣지 않는다. 「나는 관찰만 적을래」처럼 개념 이름을 대신 말해 주는 대사도 안 된다. 학생은 활동지에 적고 교사가 묻는다.
2. **한 번 읽고 이해되는가.** 「가려도 조금은 만드는데 너무 조금이라」처럼 읽는 사람이 다시 읽어야 하는 문장은 지운다. 숫자가 있으면 숫자를 적는다(「예상과 달랐다」가 아니라 「80·20 °C 를 섞어 50 °C, 100 °C 를 예상」).
3. **개념과 이어지는 논리가 문장 안에 있는가.** 장면에는 「무엇을 믿었나 → 무엇을 봤나 → 무엇이라 말했나」가 다 있어야 한다. 학생이 실험 전에 무엇을 예상했는지가 없으면 뒤의 말이 예외 처리인지 측정 의심인지 읽는 사람이 알 수 없다. 「교실에서」는 장면을 보이는 데서 끝내지 않고 **그 장면이 왜 그 개념의 증거인지**를 한 문장으로 잇는다 — 「시험 답은 외웠지만 실제로 쓰는 설명은 옛것이다」.
4. **과학교사가 실제로 겪는 장면인가.** 교사·학생이 이론의 등장인물처럼 움직이면(「봤지, 틀렸지」만 하는 교사) 상황극이다. 그런 교사가 있더라도 장면은 그 교사의 다음 말에서 시작해야지 그 교사를 조롱하는 데서 시작하지 않는다.

이 넷은 활동의 네 검사(정답·갈림·이해·상황) 가운데 「이해」와 「상황」을 장면 단위로 다시 묻는 것이다. 검토 문서의 「이렇게 정했다」에 장면을 고친 이유를 적는다.

**「교실에서」는 줄이지 말고 설명한다** (강의자 지적 2026-09-22 — 「간단히 줄여 쓴다고 명쾌해지지 않는다. 이 앱은 학생에게 교과서여야 한다」). 네 부분이 순서대로 다 있어야 한다: ① 어떤 수업의 어떤 장면인가 ② 학생·교사가 무엇을 했고 무엇이라 말했나(구체적으로, 숫자와 인용) ③ 결과 ④ **왜 이것이 이 개념의 예인가** — 개념 낱말을 직접 써서 한두 문장. ④가 없으면 읽는 사람은 두 설명을 견준 것인지 이은 것인지 모른다. 문장은 짧게(60자) 두되 문장 수는 3~9로 둔다(`verify:concepts`). 본보기: 교수법 5강 카드 3 「설명력」.

## 하지 않는 것

- 부품(`src/components`) · 검증기(`scripts`) · 다른 차시 파일을 고치지 않는다. 검증기가 틀린 것 같으면 고치지 말고 보고한다.
- 강사 대본·타임라인·학생 발화 인용·판(tier)·형성평가·재응답 — 새 타입에 없다. 넣지 않는다.
- Windows: Bash heredoc·`node -e` 로 파일을 쓰지 않는다. Write·Edit 도구로 쓴다.
